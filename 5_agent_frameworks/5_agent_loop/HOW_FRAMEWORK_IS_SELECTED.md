# How the Orchestrator Selects a Framework

The orchestrator LLM chooses a framework key from the discovered team. There is no Python routing algorithm that decides that Strands is best for greetings or Agno is best for verbs.

The overall process is:

```text
Python discovers the available frameworks
        ↓
The prompt shows their framework keys to the orchestrator LLM
        ↓
The prompt tells the LLM to use every discovered framework
        ↓
The LLM chooses their order and assigns distinct objectives
        ↓
The LLM passes a framework key to launch_worker
        ↓
team.by_key maps the key to the corresponding worker script
```

## 1. Python discovers the available frameworks

`catalog.discover()` checks which worker files exist and returns records such as:

```python
[
    {"key": "strands", "file": "../2_strands_pydantic/strands_worker.py", ...},
    {"key": "pydantic", "file": "../2_strands_pydantic/pydantic_worker.py", ...},
    {"key": "maf", "file": "../3_maf_agno/maf_worker.py", ...},
    {"key": "agno", "file": "../3_maf_agno/agno_worker.py", ...},
    {"key": "mastra", "file": "../4_mastra/worker.ts", ...},
]
```

Missing worker files are excluded. Therefore, the orchestrator only receives frameworks whose worker files currently exist.

## 2. `Team` creates a routing table

`Team.__init__()` in `orchestrator.py` creates:

```python
self.by_key = {
    w["key"]: w
    for w in workers
}
```

With all five workers, the result is conceptually:

```python
team.by_key = {
    "strands": <Strands worker record>,
    "pydantic": <Pydantic worker record>,
    "maf": <MAF worker record>,
    "agno": <Agno worker record>,
    "mastra": <Mastra worker record>,
}
```

This dictionary is the actual routing table. A framework key is translated into the manifest record that contains its worker file and runner type.

## 3. The framework list is inserted into the LLM prompt

`_build_agent()` converts the discovered workers into text:

```python
team_lines = "\n".join(
    f"- {w['name']} (framework key: {w['key']}, folder: {w['slug']}/)"
    for w in team.workers
)
```

With every worker available, the model sees:

```text
- AWS Strands (framework key: strands, folder: strands/)
- Pydantic AI (framework key: pydantic, folder: pydantic/)
- Microsoft Agent Framework (framework key: maf, folder: maf/)
- Agno (framework key: agno, folder: agno/)
- Mastra (framework key: mastra, folder: mastra/)
```

The model therefore knows the legal framework strings.

## 4. The prompt tells the model to use every framework

`ORCHESTRATOR_PROMPT` instructs the model to do the following for each discovered framework:

1. Choose a different language-learning objective.
2. Call `launch_worker` with that framework key and objective.
3. Start all builders before calling `wait_for_team`.

The model might decide on a mapping such as:

```text
strands   → greetings
pydantic  → numbers
maf       → food and drink
agno      → common verbs
mastra    → colours and shapes
```

This mapping is generated by the LLM. It is not hard-coded in Python, and a later run may choose different objectives or a different launch order.

## 5. The model emits a structured tool call

The orchestrator LLM produces a tool request conceptually equivalent to:

```json
{
  "name": "launch_worker",
  "arguments": {
    "framework": "strands",
    "objective": "Greetings and Introductions"
  }
}
```

Google ADK finds the registered Python tool named `launch_worker` and invokes:

```python
launch_worker(
    framework="strands",
    objective="Greetings and Introductions",
)
```

The example does not mean Strands must be first or must receive greetings. Both decisions are dynamic.

## 6. Python validates the framework key

Inside `launch_worker()`:

```python
worker = team.by_key.get(framework)
```

For:

```python
framework = "strands"
```

the lookup becomes:

```python
worker = team.by_key.get("strands")
```

and returns the Strands worker record.

If the model supplies an invalid key such as:

```python
framework = "crewai"
```

then the lookup returns `None`, and the tool responds with:

```text
No builder named 'crewai'. Your team is: strands, pydantic, maf, agno, mastra.
```

The model can read that result and try again with a valid key.

The tool also prevents duplicate initial launches. If the selected worker already has an objective in `team.objectives`, it returns a message saying that the worker is already building a game.

## 7. The worker record determines the executable

After the key is validated, `_launch()` calls:

```python
catalog.launch_argv(
    worker=worker,
    task_id=goal_id,
    board_path=team.board_path,
)
```

The selected worker record determines the executable:

| Framework key | Worker | Command type |
|---|---|---|
| `strands` | `strands_worker.py` | `uv run` |
| `pydantic` | `pydantic_worker.py` | `uv run` |
| `maf` | `maf_worker.py` | `uv run` |
| `agno` | `agno_worker.py` | `uv run` |
| `mastra` | `worker.ts` | `npx tsx` |

For example:

```text
framework="agno"
        ↓
team.by_key["agno"]
        ↓
Agno worker manifest record
        ↓
catalog.launch_argv(...)
        ↓
uv run .../agno_worker.py <goal_id> <board_path>
```

## What the LLM and Python each decide

The orchestrator LLM decides:

- Which discovered framework to launch next.
- Which learning objective to assign to it.
- The order in which it makes the tool calls.

Python decides:

- Which frameworks are available based on file existence.
- Whether the supplied framework key is valid.
- Whether that framework has already received an initial assignment.
- Which physical worker file corresponds to the key.
- Whether to launch that worker with `uv run` or `npx tsx`.

The program does not compare framework capabilities or select a technically superior framework for a particular objective. Every discovered framework is intended to receive one objective, and the LLM simply creates a distinct assignment and launch order for each one.
